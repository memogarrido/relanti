ARQ Relanti · v0.1

Architecture

Two native apps, one Kotlin core, as little personal data as possible

This turns design proposal v0.3 into a technical plan. It covers where the shared logic lives, accounts with Firebase, Sentry, analytics and the GDPR position. It also covers payments, the content pipeline from the BOE, the animated GPS and the evolving car. Each section recommends one option, and the decisions that are yours are listed at the end.

The short answer
  1. Shared logic in a Kotlin Multiplatform core. Study rules, scheduling, points, the Semáforo, content loading, sync and entitlements are written once. SwiftUI and Compose stay fully native and only draw what the core tells them.
  2. Local-first, account optional. The app works fully with no account and no network, like Volantón. An account only backs up and syncs progress.
  3. Firebase for sign-in and backup: Auth with Sign in with Apple and Google, plus Firestore in an EU region. No Firebase Analytics, Crashlytics or push.
  4. Sentry in its EU region for crashes, and TelemetryDeck for anonymous analytics. Both are off until the learner says yes once, with no identifiers and no IP storage.
  5. Progress is stored as an append-only log of rounds. Points, upgrades, reviews and the Semáforo are computed from it, so sync is a simple merge, nothing ever goes down, and the account holds almost nothing personal.
  6. Native StoreKit 2 and Play Billing for the one-time payment, with the free-tier rules in the shared core.
PK 1 Principles

Four rules every component follows

The device is the source of truth

Progress lives in a local SQLite database. The cloud is a copy for backup and a second device. If Firebase disappeared tomorrow, nobody would lose a single tramo.

Collect only facts we can't compute

We store what happened (which questions, right or wrong, when) and derive everything else. There are no profiles, names, ages or locations.

Nothing leaves the phone without a reason

With no account and no consent, the only network call is the optional content pack download, which carries no identifier. Every other request is tied to a choice the learner made.

Logic once, pixels twice

Anything that decides something lives in the shared core and is tested there. Anything you see or hear is native, so the apps feel at home on each platform.

PK 3 Shared logic

Kotlin Multiplatform for the core, native for everything you see

Volantón shared only data: content/ and the spec/ cases that both apps had to pass, with the rules written twice. That worked for a kids app with simple rules. Relanti has much more logic: spaced review, two-day mastery, licence points, the Semáforo, the free tier, sync merging and template-generated questions. Writing that twice means two sets of bugs, and these are the bugs that cost a learner their progress.

Shared · shared/

Decides

  • Domain models: etapa, tramo, item, truco, round, car config.
  • Feature state machines exposed as StateFlow<UiState> plus intents: TramoSession, Simulacro, ITV, Retrovisor, Ruta.
  • Rules: good round (≤1 mistake), two different days for a ticket, review intervals, Puntos negros, licence points, upgrade thresholds 3·6·8·12·15.
  • Turbo's mood: which expression to show for each event, and blink and spinner timings.
  • Access: what is free, and "never lock what you started".
  • Sync engine, consent state and a telemetry API with an allow-list of events.
Native · iosApp/ androidApp/

Draws and talks to the OS

  • Every screen, navigation, Dynamic Type, VoiceOver and TalkBack.
  • GPS eyes as SwiftUI and Compose Canvas shapes, driven by the shared mood.
  • Car compositing from layered renders.
  • StoreKit 2 and Play Billing, behind a shared Store interface.
  • Firebase SDKs (official ones), behind shared AuthGateway and RemoteLog interfaces.
  • Text to speech, local notifications and share cards.

How iOS consumes it

Gradle builds RelantiCore.xcframework, which the Xcode project embeds through a build phase. SKIE makes the Kotlin API feel like Swift: sealed classes become Swift enums, flows become AsyncSequence, and suspend functions become async. A thin @Observable wrapper per feature feeds SwiftUI. When Kotlin's own Swift export is stable we can drop SKIE.

Libraries in the core

Only small, multiplatform, well-kept ones: kotlinx.coroutines, kotlinx.serialization, kotlinx-datetime for "two different days" in the learner's time zone, and SQLDelight for the database. There is no DI framework: one RelantiCore object wires everything, and each app gives it its platform pieces at start-up.

Tests

Volantón's spec/ cases become commonTest fixtures that run on JVM and iOS simulators in CI. One example: "8 questions, 1 miss, on 3 Nov and again on 5 Nov earns ticket SE-101". UI gets snapshot tests per platform (Paparazzi, swift-snapshot-testing) in light and dark.

The cost: the iOS build depends on Gradle and a JDK, the first build is slow, and debugging Kotlin from Xcode needs the xcode-kotlin plugin. The framework adds a few MB to the app. All of this is manageable for a two-app team, and it pays back the first time a rule changes.

PK 5 Progress data

Store what happened, compute the rest

The core keeps an append-only log of rounds. A round is one tramo, Retrovisor session, ITV or simulacro, with its answers. Everything the learner sees is a pure function of that log plus the content pack.

// what is stored and synced (per learner)

      startedAt: Instant, tz: "Europe/Madrid", contentVersion: 42,
      answers: [Answer(item: "SE-101-07", choice: B, correct: false, ms: 9400)])
Milestone(id, kind: POINT|UPGRADE|APROBADO, key: "etapa:SE", at)   // once earned, kept
Settings(car: {body, colour, name}, gpsName, examDate?, dailyTime, voice, updatedAt)

// computed by the core, never stored remotely
tickets, magnets, licence points, upgrades, km, días al volante,
Retrovisor queue, Puntos negros, Semáforo, Hoja de ruta

Why a log

  • Sync is a union. Rounds have UUIDs and never change, so two phones merge without conflicts. Settings are one small record, where the latest write wins.
  • Rules can change safely. If we tune the review intervals, the core recomputes from history.
  • Nothing goes down. Points and upgrades are recorded as milestones the first time they're earned, so a retired question or a rule change never takes one away.
  • Export is trivial. "Descargar mis datos" writes the log as JSON.

Stable ids

Items are named tramo-number, and a template-generated item keeps its id when a fact changes, because the id comes from the template and its parameter key, not from the text. Codes are never renumbered. A retired item stays in the log and drops out of reviews.

A full year of daily study comes to a few thousand rounds, under 5 MB. That's trivial on the device and well inside Firestore's free quota.

PK 6 Accounts

Firebase, used narrowly

Firebase is a good fit for sign-in and backup: it's cheap at this scale, has mature native SDKs and handles Sign in with Apple well. The GDPR position comes from using only the two pieces we need and keeping personal data out of them.

Use

Firebase Auth

  • Sign in with Apple and Google only, so there are no passwords to store or reset. Apple users can hide their email.
  • It's offered after the first etapa, as "Guarda tu progreso", and on a second device. It never blocks study.
  • On sign-in the local log uploads, and a log already in the cloud merges in.
Use

Firestore, EU region

  • Create the project with eur3 (Belgium and Netherlands) or europe-southwest1 (Madrid). The region can't be changed later.
  • Path users/{uid}/rounds/{roundId} and users/{uid}/meta/settings. Security rules allow each uid to touch only its own documents.
  • The core's outbox pushes new rounds in batches, offline-safe.
  • App Check (App Attest and Play Integrity) keeps scripts out of the database.
Don't add

The rest of Firebase

  • Google Analytics for Firebase: it ties into Google's ad stack, so it needs consent and makes the privacy labels harder.
  • Crashlytics: Sentry covers it, in the EU.
  • Cloud Messaging: the one daily nudge is a local notification, so no push token is needed.
  • Remote Config and A/B testing aren't needed for v1.

Deleting an account

Apple requires in-app deletion. "Borrar cuenta" calls one Cloud Function that deletes users/{uid} and the Auth user. Local progress stays on the phone unless the learner also chooses "Borrar todo". Accounts with no activity for 24 months get an email warning and are then deleted.

Cross-platform purchases (later)

In v1 a purchase unlocks that store's app and is restored from the store. Later, a second Cloud Function can verify a receipt and write an entitlement to the account, so buying on iPhone also unlocks Android. Apple's rules allow this for content bought on another platform.

If you'd rather stay EU-only

Firebase Auth isn't region-pinned, so Google processes it under its DPA and the EU-US Data Privacy Framework. If you want everything hosted in the EU, Supabase in Frankfurt is the alternative. Auth and sync sit behind the core's interfaces, so switching later only touches those two adapters.

PK 7 Monitoring and analytics

Sentry for crashes, TelemetryDeck for usage, both by consent

Sentry

  • An organisation in the EU data region (Frankfurt).
  • sentry-kotlin-multiplatform in the core, so Kotlin exceptions on iOS get proper stack traces. It wraps the native Cocoa and Android SDKs.
  • sendDefaultPii = false, "Prevent storing of IP addresses" on, no user set, and no session replay or screenshots.
  • A beforeSend hook strips breadcrumbs down to screen names and drops any free text.
  • Release health on, tracing at 5% or less, and the shortest retention on the plan.

TelemetryDeck

  • A Germany-based, privacy-first analytics service with Swift and Kotlin SDKs. It uses no IDFA or ad ID, and only a salted hash per install.
  • It's called through the core's Telemetry API, which accepts only events on a reviewed allow-list. Nobody can log a question's text or a name by accident.
  • Events cover the funnel (onboarding done, first ticket, first simulacro, Aprobado), paywall seen and bought, and item difficulty: item id, right or wrong. That last one is what tells us which questions are badly worded.

Why not PostHog or Firebase

PostHog EU is the stronger option if you later want session-level funnels or feature flags. Its SDKs are heavier, though, and default to person profiles we would have to switch off. Firebase Analytics is ruled out above. TelemetryDeck answers the questions a study app has, with the least data.

Proposed · one consent card

After choosing the car, Turbo asks once: "¿Me ayudas a mejorar?" There are two switches, Informes de errores and Estadísticas anónimas, both off, with buttons "Activar las dos" and "Ahora no" of equal weight. It can be changed any time in Yo › Privacidad. Spain's LSSI art. 22.2 and the AEPD's guidance treat SDK storage on the device like cookies, and opt-in removes the argument. The core only initialises Sentry and TelemetryDeck after a yes. If a lawyer confirms that crash reports with no identifiers count as strictly necessary, that one switch can default to on.

What this buys you

  • No ATT prompt on iOS, because nothing tracks.
  • Short privacy labels: with an account, email and user id are linked; diagnostics and usage are not linked and only collected with consent.
  • No special categories and no minors' data issues: learners are 17 or older, above Spain's digital consent age of 14 (LOPDGDD art. 7).
  • Easy rights requests: access and portability are the in-app export, and erasure is the delete button.

Paperwork, once

  • Accept the Google Cloud, Sentry and TelemetryDeck DPAs.
  • A short privacy policy in Spanish built from the table above, linked from Yo and from both stores.
  • A one-page record of processing (art. 30). With this little data, a DPIA isn't required.
  • Have a lawyer review the policy and the consent card once before launch.
PK 9 The toll

One non-consumable purchase per store

Stores

One non-consumable product, autopista, on each store. On iOS, StoreKit 2 verifies the signed transaction on the device and Transaction.currentEntitlements restores it. On Android, Play Billing returns the purchase, which we acknowledge, and queryPurchasesAsync restores it. Both report to the core as Entitlement.Autopista or Entitlement.Free.

Rules live in the core

The free tier (the first 3 etapas, 1 simulacro a day, points up to 3 and the first upgrade) and "anything you started stays open" are shared code with tests. The paywall is just one more state a screen can be in: the grey "Autopista de peaje" exit sign.

Why not RevenueCat

For one product with no subscriptions it adds a processor and a customer id for no gain. It's worth reconsidering only if subscriptions or cross-platform entitlements without accounts ever come up.

PK 10 Content pipeline

From the BOE to a signed pack

This is v0.3's content plan expressed as components.

Source

content/ holds YAML: fact tables (speeds, alcohol limits, distances, points), question templates over them, hand-written items, trucos and media. Each record has its BOE block (for example BOE-A-2003-23514 · a48), a fingerprint of that article's text, and a "checked on" date.

Compile

tools/contentc uses the core's own models to expand the templates, check ids, sources, images and copy keys, and write content-<version>.db (SQLite) plus a manifest. The pack is signed with an Ed25519 key that lives only in CI secrets.

Watch

A weekly GitHub Action reads the three laws from the BOE's consolidated legislation API, compares the fingerprints and opens an issue listing the affected items with the old and new text. A DGT news watch feeds the "Novedad" trucos.

Fix

Claude drafts the updated items in a pull request and a person approves it. CI recompiles and runs every spec case against the new pack.

Ship

Every app release bundles the latest pack. Optionally, the app checks manifest.json on a static CDN about once a day. It downloads a newer pack only if the signature verifies and its schema version matches the app, and the request carries no identifier. Firebase Hosting or Cloudflare R2 both work.

Fixing a question

Edit the YAML, or a fact cell for template questions, in a pull request. CI recompiles the pack and runs the spec cases. On merge, a "Publish content" workflow you approve by hand uploads the pack to the beta channel, which TestFlight and internal builds read. After a check on a real phone, a second click promotes it to stable.

Adding new questions

New items or a new tramo go into content/ with new ids, never renumbering old ones. They ship the same way and show up in their etapa on the next launch. Paid etapas are already in every pack, and the core opens them when the learner is entitled, so a purchase never needs a download.

When an app release is needed

Each pack declares a schemaVersion. New questions, fixes, trucos, images and copy only need a pack. A new question format or a new screen needs an app release, and older apps keep the last pack they understand.

Progress refers to item ids and records the contentVersion for each round, so a new pack never breaks history. A changed item counts as new for the Retrovisor, but tickets and points already earned stay.

PK 11 GPS and car

Characters as data plus native drawing

The animated GPS

  • The device is a rendered image from Scripts/turbo/turbo.py. The eyes are vector shapes drawn on top: SwiftUI Canvas with TimelineView, and Compose Canvas with animate*AsState.
  • The core's TurboMood state machine turns events into expressions: idle (blink every 3 to 5 s), curious (on a Salida), happy (on a right answer), explain (on a truco), recalculando (on a miss), and silent with only a clock in simulacros.
  • Shapes and timings come from one gps-eyes.json in the content pack, so both platforms match and a designer can tune them without a release.
  • It respects Reduce Motion. Voice uses on-device TTS, with no network.

The evolving car

  • Each body type (utilitario, familiar, furgo) ships as layers: a greyscale paint mask, fixed parts, and one overlay per upgrade.
  • The app tints the paint mask with the chosen colour and stacks the unlocked overlays. That's 3 bodies × 6 overlays instead of 108 flat images.
  • Which overlays show is computed by the core from licence-point milestones, so they can't drift between devices.
  • Share cards ask the core for a "no upgrades" car, so a shared image never reveals your level.
  • New bodies or upgrades are just new layers plus a row in rewards.yaml.

If we later want animation a designer authors, such as the car driving off at Aprobado, Rive has runtimes for both platforms and can sit alongside the code-drawn eyes.

PK 12 Build order

Offline first, cloud last

1 · Skeleton

Monorepo, core with the content loader, one etapa of content, both apps rendering a tramo end to end, CI green on all three builds.

2 · Offline v1

The full study loop, rewards, GPS eyes, the car, simulacros and the Semáforo, with no network at all. This is a complete, shippable app.

3 · Toll + consent

StoreKit 2 and Play Billing, the free tier, the consent card, Sentry EU and TelemetryDeck.

4 · Accounts

Firebase Auth, Firestore EU, sync, export, and the deletion function.

5 · Content packs

The signed CDN pack between releases, and the weekly law watch running in production.
